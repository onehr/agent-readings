SGLang

SGLang treats multi-call prompting, agent control flow, and structured outputs as language-model programs, then accelerates them with a Python DSL plus runtime optimizations such as RadixAttention and compressed-FSM decoding.

Why It Matters

For agents, SGLang is the serving/runtime bridge: it gives a programming surface for LM workflows and a backend that reuses KV state across calls instead of treating each call as an unrelated request.

Problem

  • LLM applications increasingly use multiple generation calls, prompting techniques, control flow, tool interaction, and structured inputs/outputs.
  • Developers often implement LM programs with brittle string manipulation, output parsing, manual parallelism, and ad-hoc synchronization.
  • General inference engines such as vLLM, TGI, and TensorRT-LLM optimize individual calls without knowing the multi-call program structure.
  • Existing engines often discard KV cache after a request, missing reuse opportunities across calls with shared prefixes.
  • Structured output decoding often masks next-token probabilities one token at a time, even when constraints permit multi-token progress.

Key gap: The paper asks how to both program and efficiently execute structured multi-call LLM workflows rather than isolated model invocations.

Method

Expose LM-program structure through a Python DSL, represent prompt state as a stream, execute branches asynchronously, retain and index KV cache in a radix tree for prefix reuse, and speed structured decoding with compressed automata.

  • Write the LM workflow as a Python-embedded SGLang program using generation and control-flow primitives.
  • Interpret the program while maintaining prompt state streams and asynchronous primitive execution.
  • When a generation call arrives, match its prefix against the RadixAttention tree.
  • Reuse matching KV-cache blocks and insert newly generated suffixes into the radix tree.
  • Evict cached prefixes with LRU-like policy when memory pressure requires it.
  • Compile structured output constraints into a compressed finite-state machine.
  • Skip token-by-token work where the FSM has deterministic multi-token paths.
  • For API-only models, speculatively issue likely future calls to hide multi-call latency.

Agent Infrastructure Takeaways

  • Agent workflows are LM programs. A serving runtime that sees the program can optimize across calls; an HTTP API that sees only isolated prompts cannot.
  • Prefix sharing is everywhere in agents: system prompts, tool schemas, retrieval context, task state, and branch roots should not be recomputed blindly.
  • RadixAttention turns prompt structure into a cache key and makes cache reuse a scheduler concern.
  • Structured output is a serving problem, not just parser cleanup. JSON/tool-call constraints can change decode speed.
  • The frontend/runtime split is useful: agent code should express control flow, while the runtime owns KV reuse, parallelism, constrained decoding, and API speculation.
  • SGLang is a bridge between agent frameworks and inference engines because it exposes enough structure for the engine to optimize agent-like workloads.

Caveats

  • The paper is an arXiv preprint and was under review in the version read.
  • The largest speedup depends on workloads with reusable prefixes or structured-output opportunities.
  • A DSL can simplify some workflows but also adds its own programming model and operational surface.
  • API speculative execution can spend money or rate limit budget on branches that are not ultimately needed.
  • RadixAttention cache management must compete with ordinary serving memory pressure and may evict useful prefixes.
  • SGLang improves execution efficiency; it does not by itself solve tool authorization, durable execution, or semantic correctness.
